# product_recommendations パーサーのブロック抽出正規表現修正 (KI-20261016-01)

**Status**: 進行中
**Date**: 2026-10-19
**Next Action**: 実行方法検討をユーザーに提示し、承認後に実装へ移行

## 意図 / 背景

known-issues/KI-20261016-01: `extract_product_recommendations`（`scripts/article/affiliate.py`）の frontmatter パーマーシングで、プロンプト指定形式（2〜3商品・各 `name`/`category`/`price_range`）が出力されていても 2項目目以降・category・price_range が脱落し、商品カードが1枚（name のみ）に縮退する。本タスクはその実行方法の検討。

## 調査結果 / 変更内容（実行方法）

### 根本原因（コード確認済み）
- `affiliate.py:874` の抽出正規表現 `r'^product_recommendations:\s*\n((?:\s*-\s+.*\n?)+)'` は「`-` 始まりの行」のみ連続キャプチャするため、最初の `- name:` 行の直後（`category:` 行）でキャプチャ終了。block は1行だけになる。
- 行単位パーサー自体（882〜902行、`- name:` 起点・`category:`/`price_range:` 継続行のペアリング）は正しい。block が不完全なだけ。
- 下流依存: `generate_article.py:385-386`（楽天APIカスケード用の Gemini 商品名抽出）と `:389-390`（`process_product_cards`）が同一関数に依存。
- 潜伏の二次リスク: `process_product_cards` の block 削除正規表現（979行、`r'^product_recommendations:\s*\n(?:[ \t].*\n?)*'`）は項目間の空行を跨げない（`[ \t]` が最低1文字を要求）。空行があると削除が途中で終わって block 残骸を frontmatter に残し、`frontmatter.py` の `validate_and_fix_frontmatter`（277行以下・ステップ1）が「破損」として block 全体を削除する経路が成立。

### 採用案（known-issues 修正方針の具体化）
1. **新しいヘルパー `_product_rec_block_span(content: str) -> tuple[int, int] | None`** を追加:
   - `re.search(r'^product_recommendations:\s*$', content, re.M)` でキー行を特定。
   - 行分割で各線の offset を計算し、キー行以降で「内容ありかつ先頭が空白でない行」（次の frontmatter キー行 or 閉じ `---`）をブロック終端として判定。
   - 返値 `(キー行の offset, block 終端の offset)`。block 内部の空行は許容（block 内に含める）。
2. **`extract_product_recommendations`**: 既存の抽出正規表現をヘルパーの span 取得に置換。block 本文（キー行込み、既存パーサーはキー行を未マッチ行として無視するため）をそのまま行パーサーへ渡す。アイテムパースロジック・返り値スキーマ（name/category/price_range）は無変更。
3. **`process_product_cards` の削除**: 既存正規表現をヘルパー span によるスライス削除に置換（抽出と一致した semantics。空行も安全）。
4. `generate_product_cards`、`_rakuten_api_keywords`、`validate_and_fix_frontmatter` などは変更しない。

### 却下した代替案
- **PyYAML ベースの frontmatter パーサー導入**: 正確性は上るが pipeline の全箇所の検証・修復ロジックを再設計する必要がありスコープ・リスク大。
- **既存正規表現に `category:`/`price_range:` 行のキャプチャ追加**: フィールド順序（name → category → price_range）に依存し、順序変更・追加フィールドに脆い。ブロック範囲化（採用案）の方が一般論的に安全。

### 境界値・既知の制限（実装後も有効）
- プロンプト形式は 2スペースインデント前提。0列の `- name:` 行（インデントなし）は block 外扱い（[] 返。現状と同一の制限）。
- `product_recommendations: []` 同行値形式は非対応（現状と同一）。
- tab インデントは空白の先頭として許容。
- block が frontmatter 末尾（`---` 直前）の場合も終端判定で処理可能。
- 行内項目順序は `name` 先頭前提（プロンプト指定）。`category:`/`price_range:` が `name:` より前に出た場合は既存パーサーのまま（直前の項目に付着、または無視）。プロンプト形式なら影響なし。
- 改行は LF 前提（既存正規表現も `\n` 前提で、回帰なし）。
- Gemini が項目 `name` を欠落させた `category:` だけ行を直前項目に付着させるケースは、プロンプト違反であり対象外。

### Gemini プロンプトとの整合性検証（2026-10-19 追加）

| kemono_story.txt | pass1（prompt_type=kemono_story） | 2026-10-19 修正: 規則を「実在商品を **1つ以上**」へ変更（例は2項目）。字段・インデントは同上 | ✅ 1件以上すべて対応（件数は上限なし・検証済み） |

補足:
- 修正案は既存正規表現の受容範囲を**包含する** superset（継続行・空行を追加して許容）のため、**現行プロンプトのすべての正当出力の再解析が保証**される
- pass2 で Gemini が block を落としてしまう可能性は低（「Frontmatter を維持」指示・「修正済み完成原稿のみ」出力）だが、仮に frontmatter 全体が失われた場合は商品カードの欠落になる（クラッシュしない、既存のリスク）。refine プロンプトに `product_recommendations` を明示追加するハードニングは別タスクで検討（コスト低だがスコープ外）。
- `data/prompt_logs/{file_timestamp}.txt` に実使用プロンプトが保存されるため、実出力との差分検証に使用可能。
- **複数記載（件数非依存）の検証（2026-10-19）**: 提案中の `_product_rec_block_span` を実装し、`docs/ai/tmp/verify_block_span.py` で検証 — 7 ケース（1件 / 2件 / 3件 / 2件+項目間空行 / **5件(3件超)** / block が frontmatter 末尾 / 無block）で **全件 ALL OK**（抽出件数、name/category/price_range 欠落なし、削除後の frontmatter 残骸なし を確認）。ブロック終端は「次のトップレベルキー行 / `---`」判定であり**件数に依存しない**ため、プロンプトの「1つ以上」指示と任意の件数に互換。検証スクリプトは docs/ai/tmp/ の使い捨て物（gitignore 対象）
