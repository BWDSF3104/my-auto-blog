# PWA 対応: Tier 1+2 実施、Tier 3 不採用

**日付**: 2026-10-22
**対象**: backlog P3 #2（PWA 対応）+ P3 #3（Service Worker）

## 選定

**Tier 1+2 を実施し、Tier 3 を不採用とする。**

| ティアー | 内容 | 判定 |
|---|---|---|
| Tier 1 | manifest.json + アイコン（icon-192/512 + favicon.svg）→ サイトインストール可能 | **実施** |
| Tier 2 | 静的アセット（`_astro/` の CSS/JS）のみ cache-first の Service Worker（SW 内 fetch は `cache: 'no-store'`） | **実施** |
| Tier 3 | 画像 50MB 上限の LRU キャッシュ管理 | **不採用**（`backlog-archive.md` #20 へ記録） |

## 根拠

- **効果**: 本サイト（個人ブログ・毎日 1 記事・静的・GitHub Pages）での PWA の主要価値は「インストール可能 + 再訪問速度向上」。画像 50MB LRU が得られるのは 1 日 ~50KB の通信節約のみ（1 記事 1 枚 / 平均 53KB・実測 199 枚）。
- **コスト**: Tier 3 の LRU ロジック（サイズ追跡・破棄・quota 監視）は SW 実装の難易度を ⭐⭐⭐ に引き上げ、かつ **304 罠**（HTTP キャッシュ経由で SW に 304 空ボディを渡す）、**ブラウザ quota 差**、**検証困難性**（quota 満杯の再現要）を伴う。
- **代替**: 画像キャッシュは「必要になった時（モバイル読者比・通信料訴求が明確になったら）」に再検討。
- **ユーザー決定**: 2026-10-22「**2までの実施、3は棄却**」（「2までの実施で終わるのは可能か？」への判断）

## 実装要点（不採用理由と無関係の設計判断）

- SW の pre-cache（`caches.open().addAll()`）は**不使用**: `_astro/*` はデプロイごとにハッシュ変更 → addAll は次回ビルドで 404 → SW 更新停止のリスク
- SW 内 fetch は `cache: 'no-store'`: HTTP キャッシュ経由の 304（空ボディ）を SW キャッシュに保持しない
- 静的アセットはハッシュ付き URL → 旧キャッシュは自動無効化（URL 変更で参照されなくなる）
- HTML / 画像 / API / search-index.json は **SW 対象外**（network 直通）
- manifest の scope: `/my-auto-blog`（GitHub Pages サブパス）

## 不採用後の再検討条件

- モバイル読者比（例: GA4 / Plausible で 50% 以上）と再訪問率が一定で確保され、画像の再取得が通信費の主要コストになるまで
- 画像の 1 記事あたりのサイズ・件数が増える（生成解像度アップ等）
