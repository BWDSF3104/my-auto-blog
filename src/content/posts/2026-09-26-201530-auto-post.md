# DSPy実践入門：プロンプトエンジニアリングを自動化する宣言的LLMプログラミング手法

## 概要と背景

大規模言語モデル（LLM）を用いたアプリケーション開発において、これまで開発者を最も悩ませてきたのは**「プロンプトエンジニアリングの試行錯誤」**です。「指示文をどう表現するか」「Few-Shotの例をどう選ぶか」「思考の過程（Chain-of-Thought）をどう促すか」といった調整はブラックボックスであり、経験則や感覚に頼る部分が多くありました。さらに、使用するLLM（GPT-4oからClaude 3.5 Sonnet、あるいはオープンソースのLlama 3など）を変更したり微調整したりするたびに、プロンプトが崩壊し、再調整を余儀なくされる問題が生じていました。

この課題を根本から解決するためにスタンフォード大学の研究チームによって開発されたのが、**DSPy（Declarative Self-Improving Language Programs）** です。

DSPyは、プロンプトを「泥臭い文字列操作」として扱うのではなく、ソフトウェアエンジニアリングにおける**「宣言的プログラミングとコンパイラ」**のパラダイムをLLM開発に持ち込みます。開発者は入出力の型（Signature）と推論ロジックの構造（Module）をコードとして定義し、プロンプトの最適化やFew-Shotの抽出、プロンプト指示文の最適化はDSPyの**Optimizer（旧称: Teleprompter）**に委ねます。これにより、LLMのバージョンアップやモデル変更にも柔軟に追従できる、持続可能で再現性の高いLLMパイプライン構築が可能になります。

---

## 技術的メカニズム・特徴

DSPyのアーキテクチャは、主に以下の3つのコア概念で構成されています。

```
+-------------------------------------------------------------------+
|                           DSPy Program                            |
|                                                                   |
|  [ Signature ]  --> Defines inputs/outputs (e.g. "context -> answer")
|        |                                                          |
|  [ Module ]     --> Applies reasoning pattern (e.g. ChainOfThought)
+-------------------------------------------------------------------+
                                 |
                                 v
+-------------------------------------------------------------------+
|                           DSPy Optimizer                          |
|                                                                   |
|  1. Generates candidate prompts / instructions                    |
|  2. Selects / bootstraps optimal Few-Shot examples                |
|  3. Evaluates against Metric & updates program weights/prompts    |
+-------------------------------------------------------------------+
```

### 1. Signatures（宣言的インターフェース）
Signatureは、プロンプトの具体的な文章を書く代わりに「何を入力とし、何を出すべきか」のタスク定義（入出力の型）のみを明示する仕組みです。

例えば、`"context, question -> answer"` という簡潔な文字列指定や、Pydantic風クラス宣言を用いて「背景情報と質問を入力に取り、最終的な回答を出力する」という契約を定義します。具体的な「プロンプト指示文」はDSPyが内部で自動生成します。

### 2. Modules（推論構造モジュール）
PyTorchにおける `torch.nn.Module` からインスピレーションを得ており、LLMの推論テクニック（Chain of Thought, ReAct, RAGなど）を抽象化したコンポーネントです。

*   `dspy.Predict`: 基本的な単一ステップのLLM呼び出し。
*   `dspy.ChainOfThought`: 思考プロセス（Reasoning Step）を挟んでから最終回答を出力するモジュール。
*   `dspy.ReAct`: 外部ツール（検索APIや計算機）を試行錯誤しながら利用するエージェントモジュール。

これらを組み合わせることで、複雑なマルチステップのパイプラインをコードとして組み上げることができます。

### 3. Optimizers（自動コンパイルとプロンプト最適化）
DSPyの最も革新的な機能です。最適化アルゴリズム（例: `BootstrapFewShot`, `MIPROv2`）は、少数の訓練データセット（数十件〜数百件程度）と**評価関数（Metric）**を受け取り、以下の処理を自動的に実行してプログラムを「コンパイル（最適化）」します。

1.  **Bootstrapping**: パイプラインを試行実行し、成功した推論ステップ（思考プロセスやFew-Shotデータ）を自動収集する。
2.  **Instruction Optimization**: LLM自体を利用してプロンプトのシステム指示文（System Prompt）を複数パターン生成し、評価スコアが最高になる指示文を探索・選定する（MIPROv2等）。
3.  **Weight Tuning**（オプション）: 収集した高品質な推論トレースを用いてオープンモデルのファインチューニングデータを自動生成し、モデル自体をトレーニングする。

## 実装・活用コード例

ここでは、DSPyを用いて「与えられた文書（Context）と質問（Question）に基づき、回答（Answer）と確信度スコア（Confidence Score）を出力するファクトチェック付きQAパイプライン」を構築し、最適化する実装例を示します。

### 前提パッケージのインストール

```bash
pip install dspy-ai openai
```

### Python実装コード

```python
import os
import dspy
from dspy.teleprompt import BootstrapFewShot

# 1. LLMとリトリーバー（あるいは基本言語モデル）の設定
# ※ APIキーは環境変数 OPENAI_API_KEY から読み込まれます
lm = dspy.LM('openai/gpt-4o-mini', api_key=os.environ.get("OPENAI_API_KEY"))
dspy.settings.configure(lm=lm)

# 2. Signature（入出力インターフェース）の定義
class FactCheckedQA(dspy.Signature):
    """文脈情報に基づいて質問に正確に答え、回答の確信度を評価します。"""
    
    context: str = dspy.InputField(desc="回答の根拠となるテキスト")
    question: str = dspy.InputField(desc="ユーザーからの質問")
    answer: str = dspy.OutputField(desc="文脈情報のみに基づく事実に基づく回答")
    confidence: float = dspy.OutputField(desc="回答の確信度スコア（0.0 から 1.0）")

# 3. Module（推論ロジック）の定義
class RAGPipeline(dspy.Module):
    def __init__(self):
        super().__init__()
        # ChainOfThought モジュールを使用して思考プロセスを自動挿入
        self.generate_answer = dspy.ChainOfThought(FactCheckedQA)

    def forward(self, context, question):
        return self.generate_answer(context=context, question=question)

# 4. 評価メトリクス（Metric）の定義
def validate_answer(example, pred, trace=None):
    """
    正解データ(example)と予測データ(pred)を比較するカスタム評価指標
    """
    # 回答が空でないこと、かつ確信度が0.7以上であることを条件とする簡易判定
    answer_valid = len(pred.answer.strip()) > 0 and pred.answer.lower() in example.answer.lower()
    try:
        conf_score = float(pred.confidence)
        conf_valid = conf_score >= 0.7
    except ValueError:
        conf_valid = False
        
    return answer_valid and conf_valid

# 5. 訓練データセットの準備（少数のサンプル）
trainset = [
    dspy.Example(
        context="DSPyはスタンフォード大学が開発したLLMフレームワークであり、プロンプトを宣言的に記述して自動最適化します。",
        question="DSPyはどの大学で開発されましたか？",
        answer="スタンフォード大学"
    ).with_inputs('context', 'question'),
    
    dspy.Example(
        context="Python 3.12では、エラーメッセージの改善と性能向上（GILの段階的廃止準備）が行われました。",
        question="Python 3.12の主な特徴は何ですか？",
        answer="エラーメッセージの改善と性能向上"
    ).with_inputs('context', 'question')
]

# 6. 未最適化モデルの実行
uncompiled_rag = RAGPipeline()
test_context = "次世代のブラウザ標準規格としてWebGPUが登場し、クライアントサイドでのGPU計算が可能になりました。"
test_question = "WebGPUによって何が可能になりますか？"

print("=== コンパイル前（未最適化）の実行 ===")
pred_before = uncompiled_rag(context=test_context, question=test_question)
print(f"Answer: {pred_before.answer}")
print(f"Confidence: {pred_before.confidence}\n")

# 7. Optimizer (BootstrapFewShot) による自動コンパイル
print("=== DSPy Optimizer による自動最適化実行中... ===")
optimizer = BootstrapFewShot(
    metric=validate_answer,
    max_bootstrapped_demos=2,
    max_labeled_demos=2
)

# プログラムのコンパイル（最適化済みプログラムの生成）
compiled_rag = optimizer.compile(student=RAGPipeline(), trainset=trainset)

# 8. 最適化済みプログラムの実行
print("\n=== コンパイル後（最適化済み）の実行 ===")
pred_after = compiled_rag(context=test_context, question=test_question)
print(f"Answer: {pred_after.answer}")
print(f"Confidence: {pred_after.confidence}")

# 内部で自動的に組み立てられた最適化済みプロンプトの確認
print("\n=== 自動構築された最終プロンプト（一部） ===")
lm.inspect_history(n=1)
```

### コードの解説と挙動

1.  **プロンプト文を一行も記述していない点に注目**: `FactCheckedQA` クラスで構造化定義を行っただけで、指示文（System Prompt）やフォーマット指定はDSPyが内部で標準フォーマットに変換します。
2.  **`dspy.ChainOfThought`**: `FactCheckedQA` をラップすることで、LLMに対して自動的に「`Reasoning: Let's think step by step...`」という思考ステップを出力させるプロンプト構造へ拡張されます。
3.  **`optimizer.compile()`**: 事前に用意したデータセットを用いてプログラムを試行し、メトリクス（`validate_answer`）を満たす最も効果的なFew-Shotデモおよびプロンプト構造を抽出・統合します。

## まとめ

DSPyの登場は、LLM開発における大きなパラダイムシフトを意味しています。従来のプロンプトエンジニアリングが「職人技」や「試行錯誤（Trial and Error）」であったのに対し、DSPyはそれを**「構造化されたコードとアルゴリズムによる最適化プロセス」**へ昇華させました。

DSPyを採用することによる主なメリットは以下の通りです。

*   **保守性の向上**: プロンプトの長大な文字列ではなく、Pythonクラスとしてロジックを管理できる。
*   **モデルポータビリティ**: LLMを基盤モデル（GPT-4o, Claude 3.5, Llama 3等）変更時、Optimizerを再実行（コンパイル）するだけで新たなモデルに最適化されたプロンプトが自動生成される。
*   **評価主導開発（TDD/EAL）の実現**: 定量的なメトリクス（評価関数）を設定することで、プロンプト変更によるデグレを防ぎ、継続的な質の向上が可能になる。

今後は、単一のLLM呼び出しだけでなく、複数のLLMやツールが連携する複雑なAgentic AIシステムにおいて、DSPyのような「プロンプトの自動コンパイル」手法が標準的なソフトウェアアーキテクチャとして定着していくと考えられます。
