## 概要と背景

大規模言語モデル（LLM）の推論パイプラインは、大きく**Prefill（プロンプト処理）フェーズ**と**Decode（トークン生成）フェーズ**の2つに分かれます。このうち、マルチターン対話、少発事例提示（Few-shot prompting）、自己反省ループを持つAIエージェント、ドキュメントを共有するRAGなどのユースケースでは、「直前の会話履歴」や「システムプロンプト」といった**共通のプレフィックス（Prefix）トークン列が何度もLLMに入力される**という構造的特徴が存在します。

従来の推論エンジン（vLLMの初期PagerAttentionなど）は、個別リクエスト内のKVキャッシュをブロック単位で仮想メモリ管理することに優れていましたが、異なるリクエスト間、あるいは同一セッション内のターン間を跨いだPrefixの動的な再利用は静的なプロンプトキャッシュ（Static Prefix Caching）に限られていました。そのため、分岐や動的コンテキスト挿入が発生するとキャッシュヒット率が著しく低下し、大量の浮動小数点演算（FLOPs）とメモリアロケーションの重複が発生していました。

この課題を根本から解決したのが、推論フレームワーク**SGLang**で導入された**RadixAttention**です。RadixAttentionは、トークン列をキーとする基数木（Radix Tree）をメモリ上で保持し、KVキャッシュのページ構造と直接対応付けることで、任意の接頭辞マッチング、自動共有、およびキャッシュの追い出し（LRU Eviction）をO(K)（Kはトークン長）の計算量で実現します。

本記事では、RadixAttentionの核となる設計思想、内部データ構造、メモリマネージャとの協調動作を解剖し、その挙動をシミュレートするPython実装コードを通じて次世代LLMサービングの深層を解説します。

## 技術的メカニズム・特徴

### 1. RadixTreeによるトークンプレフィックスの階層管理

通常の基数木（パトリシア木）は文字列の共通部分を圧縮して保持する探索木ですが、RadixAttentionではこれを**トークンID列**に対して適用します。

各ノードは以下の情報を保持します：
- **トークンサブシーケンス (`token_ids`)**: 圧縮されたトークン列
- **KVキャッシュブロックへの参照ポインタ (`cache_indices`)**: GPU VRAM上に確保された物理KVキャッシュのスロットID
- **参照カウント (`ref_counter`)**: 現在実行中のリクエストで参照されている数（0ならEviction可能）
- **最終アクセス時刻 (`last_access_time`)**: LRUアルゴリズムによるメモリ解放のためのタイムスタンプ
- **子ノードへのエッジマップ**: 次のトークンに基づく分岐

```text
[Root] (空ノード)
   │
   └─ [System Prompt: "You are a helpful..."] (Tokens: [101, 2056, ...], KV Cache: Ptr#0-3)
         │
         ├─ [User Query A: "What is AI?"] (Tokens: [4012, 102], KV Cache: Ptr#4-5)
         │     └─ [Assistant: "AI is..."] (Tokens: [205, ...], KV Cache: Ptr#6)
         │
         └─ [User Query B: "What is ML?"] (Tokens: [5099, 102], KV Cache: Ptr#7-8)
               └─ [Assistant: "ML is..."] (Tokens: [310, ...], KV Cache: Ptr#9)
```

リクエストが到着すると、エンジンはプロンプトのトークン列でRadixTreeを根から走査し、最長一致接頭辞（Longest Common Prefix）を特定します。一致した部分については**Prefillの計算およびKVキャッシュのアロケーションを完全にスキップ**し、一致しなかったサフィックス部分のみをGPUで計算して木に新規ノードとして追加します。

### 2. 状態遷移と自動メモリリクレイム（Eviction）

GPU VRAMは有限です。RadixAttentionが真価を発揮するのは、VRAMが枯渇した際のエビクション（破棄）ロジックです。

- **ピン留め（Pinned State）**:
  現在生成中のリクエストが参照しているノードは `ref_counter > 0` となり、絶対に破棄されません。
- **解放候補（Evictable State）**:
  リクエストのデコードが完了すると、`ref_counter` はデクリメントされて `0` になります。しかし、メモリから即座にKVキャッシュを解放するのではなく、**木構造を維持したままキャッシュプールに保持**します。
- **LRUエビクション**:
  新しいリクエストのPrefillのために新規ブロックが必要になった際、利用可能な空きブロックが存在しない場合、木の中で `ref_counter == 0` かつ「最も古くアクセスされた（LRU）」リーフノードから順に切り離し、物理KVキャッシュスロットをフリーリストに返却します。

この仕組みにより、開発者が明示的にキャッシュ生存期間を管理することなく、過去の会話履歴や頻出のFew-shotプロンプトが「ベストエフォート」でVRAM上に滞留し続けます。

## 実装・活用コード例

ここでは、RadixAttentionのコアとなる「基数木に基づくKVキャッシュマネージャ」のミニマムかつ完全なPythonシミュレータを実装します。物理的なテンソル操作を除いた、プレフィックスマッチ、ノード分割（Split）、参照カウント管理、LRUエビクションのアルゴリズムを可視化します。

```python
import time
from typing import List, Dict, Tuple, Optional

class RadixNode:
    def __init__(self, token_ids: List[int], value_indices: List[int]):
        self.token_ids = token_ids          # このノードが担当するトークンID列
        self.value_indices = value_indices  # 割り当てられたKVキャッシュのスロットID
        self.children: Dict[int, "RadixNode"] = {}  # key: 先頭トークンID -> RadixNode
        self.parent: Optional["RadixNode"] = None
        self.ref_counter: int = 0           # 実行中リクエストの参照数
        self.last_accessed: float = time.time()

    def is_leaf(self) -> bool:
        return len(self.children) == 0

class RadixCacheManager:
    def __init__(self, total_slots: int):
        self.total_slots = total_slots
        self.free_slots: List[int] = list(range(total_slots))
        self.root = RadixNode(token_ids=[], value_indices=[])
        # LRUトラッキング用：ref_counter == 0 のノード集合
        self.evictable_nodes: set[RadixNode] = set()

    def _allocate_slots(self, count: int) -> List[int]:
        """空きスロットから確保。足りなければLRUでエビクションを実施"""
        while len(self.free_slots) < count:
            if not self.evictable_nodes:
                raise MemoryError("VRAM OOM: 解放可能なKVキャッシュブロックが存在しません。")
            
            # 最も古くアクセスされたノードを検索
            oldest_node = min(self.evictable_nodes, key=lambda n: n.last_accessed)
            self._evict_node(oldest_node)

        allocated = [self.free_slots.pop() for _ in range(count)]
        return allocated

    def _evict_node(self, node: RadixNode):
        """リーフノードのみ破棄可能。非リーフなら葉になるまで待つか、子供から刈り取る"""
        if not node.is_leaf():
            # リーフでない場合は、再帰的にLRUリーフを探して消す
            leaf = next(child for child in node.children.values() if child.is_leaf())
            self._evict_node(leaf)
            return

        # スロット返却
        self.free_slots.extend(node.value_indices)
        if node in self.evictable_nodes:
            self.evictable_nodes.remove(node)

        # 親からエッジを削除
        if node.parent:
            first_token = node.token_ids[0]
            del node.parent.children[first_token]
            if node.parent.ref_counter == 0 and node.parent != self.root:
                self.evictable_nodes.add(node.parent)

    def match_prefix(self, token_ids: List[int]) -> Tuple[List[int], List[int]]:
        """
        最長一致プレフィックスを探索する。
        Returns: (ヒットしたKVキャッシュインデックス, 未処理の残りトークン)
        """
        curr = self.root
        curr.last_accessed = time.time()
        idx = 0
        matched_indices = []

        while idx < len(token_ids):
            next_token = token_ids[idx]
            if next_token not in curr.children:
                break

            child = curr.children[next_token]
            edge_tokens = child.token_ids
            # 一致する長さを測定
            match_len = 0
            while (match_len < len(edge_tokens) and 
                   idx + match_len < len(token_ids) and 
                   edge_tokens[match_len] == token_ids[idx + match_len]):
                match_len += 1

            if match_len == len(edge_tokens):
                # エッジが完全にマッチしたため、さらに深く潜る
                matched_indices.extend(child.value_indices)
                idx += match_len
                curr = child
                curr.last_accessed = time.time()
            else:
                # エッジの途中で分岐（Partial Match）
                matched_indices.extend(child.value_indices[:match_len])
                idx += match_len
                break

        return matched_indices, token_ids[idx:]

    def insert(self, full_tokens: List[int], prefix_matched_len: int) -> RadixNode:
        """
        新しいトークン列を木に挿入（プレフィックスは既知、差分のみキャッシュ確保）
        """
        tokens_to_add = full_tokens[prefix_matched_len:]
        if not tokens_to_add:
            # 完全にマッチ済み
            return self.root

        # 必要な物理スロットを確保
        new_slots = self._allocate_slots(len(tokens_to_add))
        
        # 挿入位置を再探索
        curr = self.root
        idx = 0
        while idx < prefix_matched_len:
            next_token = full_tokens[idx]
            child = curr.children[next_token]
            edge_len = len(child.token_ids)
            
            if idx + edge_len <= prefix_matched_len:
                idx += edge_len
                curr = child
            else:
                # エッジの途中で分割する必要があるケース
                split_offset = prefix_matched_len - idx
                # 分割処理
                curr = self._split_node(child, split_offset)
                idx = prefix_matched_len
                break

        # 新規ノードをcurrの子として作成
        new_node = RadixNode(token_ids=tokens_to_add, value_indices=new_slots)
        new_node.parent = curr
        curr.children[tokens_to_add[0]] = new_node
        
        # 参照カウントを1に初期化
        new_node.ref_counter = 1
        if curr in self.evictable_nodes:
            self.evictable_nodes.remove(curr)

        return new_node

    def _split_node(self, node: RadixNode, split_offset: int) -> RadixNode:
        """ノードを2つに分割し、共通親ノードを新設する"""
        parent = node.parent
        split_token = node.token_ids[split_offset]

        # 前半ノード（中間ノード）
        mid_node = RadixNode(
            token_ids=node.token_ids[:split_offset],
            value_indices=node.value_indices[:split_offset]
        )
        mid_node.parent = parent
        parent.children[node.token_ids[0]] = mid_node

        # 後半ノード（元のノードの残余）
        node.token_ids = node.token_ids[split_offset:]
        node.value_indices = node.value_indices[split_offset:]
        node.parent = mid_node
        mid_node.children[split_token] = node

        return mid_node

    def release(self, node: RadixNode):
        """リクエスト終了時の参照カウント減少"""
        curr = node
        while curr != self.root:
            curr.ref_counter -= 1
            if curr.ref_counter == 0:
                self.evictable_nodes.add(curr)
            curr = curr.parent


# 実行デモ
if __name__ == "__main__":
    # キャッシュスロット全体を20個とする小さなプール
    manager = RadixCacheManager(total_slots=20)

    # 共通システムプロンプト: [1, 2, 3]
    system_prompt = [1, 2, 3]
    # Request 1: [1, 2, 3] + Query A [10, 11]
    req1_tokens = system_prompt + [10, 11]

    print("=== Request 1 到着 ===")
    hit_slots, remaining = manager.match_prefix(req1_tokens)
    print(f"Prefixヒットスロット: {hit_slots}, 残り計算トークン: {remaining}")
    req1_node = manager.insert(req1_tokens, len(hit_slots))
    print(f"割当後 空きスロット数: {len(manager.free_slots)}")

    # Request 1 終了
    manager.release(req1_node)

    # Request 2: [1, 2, 3] + Query B [20, 21] (System Promptが共通)
    req2_tokens = system_prompt + [20, 21]
    print("\n=== Request 2 到着 (分岐プロンプト) ===")
    hit_slots, remaining = manager.match_prefix(req2_tokens)
    print(f"Prefixヒットスロット: {hit_slots}, 残り計算トークン: {remaining}")
    # [1, 2, 3] のKVキャッシュが完全再利用され、[20, 21] の2トークン分のみ計算
    req2_node = manager.insert(req2_tokens, len(hit_slots))
    print(f"割当後 空きスロット数: {len(manager.free_slots)}")
```

### 実行結果の分析

上記スクリプトを実行すると、Request 2 が到着した段階で、Prefillを丸ごとやり直すことなく `[1, 2, 3]` のスロットID（3トークン分）が即座にヒットし、未処理の `[20, 21]` の2スロットのみが新規消費されることが確認できます。

マルチターン対話では、会話が深くなるにつれてヒット率が飛躍的に高まり、Time-To-First-Token（TTFT: 最初の1トークン目が出力されるまでの時間）が大幅に削減されます。

## まとめ

RadixAttentionは、単なるプロンプトキャッシュの最適化を超えて、**「推論エンジン自体を階層木構造のインデックスを持つオペレーティングシステムにする」** というパラダイムシフトをもたらしました。

1. **ゼロ・オーバーヘッド共有**: 分岐する対話履歴や木探索型推論（Tree-of-Thought, MCTS）において、枝分かれしたコンテキストのKVキャッシュを重複ゼロで共有可能。
2. **自動かつ柔軟なリソース管理**: 事前にPrefixキャッシュの境界をエンジニアが定義する必要がなく、RadixTreeとLRUにより動的に最適化。
3. **TTFTとスループットの飛躍的改善**: 冗長なAttention計算を排除することで、GPU演算器（Tensor Core）をPrefillの再計算から解放し、純粋なGenerationにリソースを集中可能。

LLMを活用した複雑な自律エージェントや推論時計算（Inference-time Compute）の拡大に伴い、推論基盤におけるRadixAttentionのような動的メモリマネジメント技術は、これからのAIエンジニアにとって必須の基盤知識となるでしょう。
