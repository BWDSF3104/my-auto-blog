## 概要と背景

大規模言語モデル（LLM）を外部システムやエンタープライズのバックエンドAPI、データベースと連携させる際、最大の障壁となってきたのが「出力の非決定性と構文エラー」です。システム間連携では、厳格なJSONスキーマやSQL、特定のドメイン固有言語（DSL）に1文字たりとも狂いなく準拠することが要求されます。

従来の解決アプローチは、主にプロンプトエンジニアリングやFew-Shotプロンプティング、モデルのファインチューニング（Function Callingチューニング）に依存していました。しかし、確率的に次のトークンをサンプリングする自己回帰型デコーディングの性質上、確率がゼロにならない限り構文エラー（括弧の閉じ忘れ、不正なデータ型、エスケープ漏れ）の発生は避けられません。リトライ処理やパースエラー時の自己修復プロンプトは、レイテンシとトークンコストを大幅に悪化させます。

そこで登場し、vLLM、Outlines、SGLang、そしてOpenAI APIの公式「Structured Outputs」などの基盤技術として標準化されたのが**制約付きサンプリング（Constrained Sampling / Guided Decoding）**です。

本記事では、プロンプトに頼らず「推論アルゴリズムの内部で不正なトークンを物理的にサンプリング不可能にする」アプローチの数理的背景と、有限状態機械（FSM: Finite State Machine）および文脈自由文法（CFG: Context-Free Grammar）を用いたロジットマスキングのメカニズムを解説し、Pythonによる最小限の実装コードを示します。

## 技術的メカニズム・特徴

制約付きサンプリングの本質は、言語モデルの推論ループ（Forward Pass）と形式言語理論におけるオートマトン（Autoamata）の統合にあります。

### 1. 自己回帰デコードとロジットマスキング

自己回帰LLMは、ステップ $t$ において語彙辞書 $V$（サイズ $|V| \approx 32,000 \sim 128,000$）内の全トークンに対する非正規化対数確率（ロジットベクトル $\mathbf{z}_t \in \mathbb{R}^{|V|}$）を出力します。通常はこれをソフトマックス関数に通して確率分布 $P(w_t)$ を算出します。

$$P(w_t = v_i \mid w_{<t}) = \frac{\exp(z_{t, i})}{\sum_{j \in V} \exp(z_{t, j})}$$

制約付きサンプリングでは、現在の生成状態において文法的に許容されるトークンの部分集合 $V_{\text{valid}} \subseteq V$ を特定し、許可されないトークンのロジットを $-\infty$（実用的には浮動小数点の極小値 $-1e9$）に書き換えます（**ロジットマスキング**）。

$$z_{t, i}' = \begin{cases} z_{t, i} & (v_i \in V_{\text{valid}}) \\ -\infty & (v_i \notin V_{\text{valid}}) \end{cases}$$

ソフトマックス関数を通過させると、許容されないトークンの生成確率は厳密に 0 となり、モデルは**文法的に正しいトークンの中から最も文脈に適したトークンのみを選択**することになります。

### 2. トークナイザの不確定性とFSM（正規表現）

単純なアプローチでは「1文字ずつチェックする」と考えがちですが、LLMは文字ではなくサブワード単位（BPEやSentencePiece）でトークン化されています。例えば、JSONの数値フィールドを生成する際、許容される文字は数字 `[0-9]` ですが、トークン辞書には `"1"`, `" 12"`, `"999"`, `"abc"` など多様な断片が存在します。

この課題を解決するため、正規表現やPydanticスキーマから**決定性有限オートマトン（DFA / FSM）**を構築し、トークン辞書全体と事前突合するインデックス化手法が用いられます。

```
[正規表現 / JSON Schema]
         │
         ▼
[決定性有限オートマトン (FSM)] ── (状態遷移: S0, S1, S2...)
         │
         ▼ 事前コンパイル / キャッシュ
[状態別 有効トークンインデックス]
  状態 S0 で受容可能なトークン集合: { "{\"", " {", ... }
  状態 S1 で受容可能なトークン集合: { "name", "age", ... }
```

1. **事前マッピング**: 正規表現からDFAの状態遷移図を作成。
2. **語彙の仮想走行**: 語彙辞書内の各トークン（文字列）を各DFA状態に入力した際、どの状態へ遷移可能かを事前に計算・キャッシュ。
3. **推論時**: 現在のDFA状態に応じた許容トークンマスクを取り出し、GPU上のロジットに加算（$O(1)$に近い高速なマスク処理）。

### 3. CFG（文脈自由文法）による再帰的スキーマの処理

ネストが深いJSONやプログラミング言語の構文など、正規表現（有限状態）では表現できない再帰構造に対しては、**LR/Earleyパーサーに基づく文脈自由文法（CFG）**が利用されます。パーサーの状態スタックに応じて次に来訪可能な終端記号（トークン）を決定し、同様にロジットをフィルタリングします。

## 実装・活用コード例

ここでは、Hugging Faceの `transformers` ライブラリの内部フック機構である `LogitsProcessor` を自作し、指定した正規表現に適合するトークンのみを選択させる最小限の「FSM制約付きデコーディング」を実装します。

### 1. カスタムLogitsProcessorの実装

以下のコードは、Python標準の `re` モジュールを模したシンプルな状態判定を用いて、生成文字列が特定のパターン（例: 正しいJSONブール値または特定プレフィックス）に合致するトークンのみにロジットを制約します。

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, LogitsProcessor, LogitsProcessorList

class RegexLogitsProcessor(LogitsProcessor):
    """
    生成中のテキストが指定された正規表現のプレフィックスに一致する
    トークンのみをサンプリング可能にするLogitsProcessor
    """
    def __init__(self, pattern: str, tokenizer, prompt_length: int):
        import regex
        self.pattern = regex.compile(pattern)
        self.tokenizer = tokenizer
        self.prompt_length = prompt_length
        self.vocab = tokenizer.get_vocab()
        
    def __call__(self, input_ids: torch.LongTensor, scores: torch.FloatTensor) -> torch.FloatTensor:
        # 現在のバッチサイズと生成済みトークン系列を取得
        # ここでは単一シーケンス (batch_size=1) を想定
        generated_ids = input_ids[0, self.prompt_length:]
        current_text = self.tokenizer.decode(generated_ids, skip_special_tokens=False)

        # マスクの初期化 (-inf で埋める)
        mask = torch.full_like(scores, fill_value=-float("inf"))

        # 全トークンに対して、現在のテキストに追加した文字列が
        # 正規表現の部分一致（prefix match）を満たすかを判定
        # ※ 実運用ライブラリ(Outlines等)ではこのループを事前計算・インデックス化して高速化します
        valid_token_ids = []
        for token_str, token_id in self.vocab.items():
            candidate_text = current_text + token_str
            # candidate_text が pattern の先頭から成立し得るかを検査
            match = self.pattern.fullmatch(candidate_text, partial=True)
            if match:
                valid_token_ids.append(token_id)

        if not valid_token_ids:
            # マッチする候補がない場合はEOSトークンを許可して停止
            mask[0, self.tokenizer.eos_token_id] = 0.0
        else:
            mask[0, valid_token_ids] = 0.0

        # 元のスコアにマスクを加算
        return scores + mask
```

### 2. モデルによる推論の実行

作成したプロセッサを組み込み、指定スキーマ（例: `{"status": "OK" | "ERROR", "code": [0-9]{3}}`）に100%強制準拠させます。

```python
# モデルとトークナイザの準備（小型モデルで実証）
model_name = "Qwen/Qwen2.5-0.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float32)

prompt = "システムのヘルスチェック結果をJSON形式で出力してください。\n出力:"
input_ids = tokenizer.encode(prompt, return_tensors="pt")

# 生成させたい厳密な正規表現
# 例: {"status": "OK" または "ERROR", "code": 3桁の数字}
strict_pattern = r'\{"status": "(OK|ERROR)", "code": [0-9]{3}\}'

logits_processor = LogitsProcessorList([
    RegexLogitsProcessor(strict_pattern, tokenizer, prompt_length=input_ids.shape[1])
])

output = model.generate(
    input_ids,
    max_new_tokens=40,
    logits_processor=logits_processor,
    do_sample=True,
    temperature=0.7,
    pad_token_id=tokenizer.eos_token_id
)

generated_text = tokenizer.decode(output[0][input_ids.shape[1]:], skip_special_tokens=True)
print("=== 生成結果 ===")
print(generated_text)
```

### 3. Outlinesライブラリを用いたプロダクションでの実用例

本番環境では、FSMの事前構築とRust/C++によるインデックスキャッシュを実装したライブラリ（`outlines`）を利用することで、オーバーヘッドをほぼゼロに抑えられます。

```python
import outlines
from pydantic import BaseModel, Field

# 出力スキーマをPydanticで厳密に定義
class UserProfile(BaseModel):
    name: str = Field(pattern=r"^[A-Z][a-z]+$")
    age: int = Field(ge=0, le=120)
    role: str = Field(pattern=r"^(admin|editor|viewer)$")

model = outlines.models.transformers("Qwen/Qwen2.5-0.5B-Instruct")
generator = outlines.generate.json(model, UserProfile)

result = generator("新規登録ユーザー「John」、30歳、権限は管理者を抽出してください。")
print(result)
# 出力: UserProfile(name='John', age=30, role='admin')
# -> 形式崩れや型不整合は確率論的に 0% となる
```

## まとめ

制約付きサンプリング（Guided Decoding）は、LLMの持つ「自然言語理解と常識推論の能力」を維持したまま、「形式的整合性」を形式言語理論によって完全に担保する技術的ブレイクスルーです。

| 手法 | 準拠信頼性 | 推論オーバーヘッド | 導入の複雑さ |
| :--- | :--- | :--- | :--- |
| **Few-Shot / プロンプト指示** | 中〜低（確率的失敗あり） | なし | 極めて容易 |
| **JSON Mode（ファインチューニング）** | 高（稀にパース失敗） | なし | モデル依存 |
| **制約サンプリング（FSM/CFG）** | **100%（数学的保証）** | 初期化コスト（推論時は極小） | 推論エンジン側の対応要 |

今後は、単なるJSON出力の保証にとどまらず、プログラミング言語のコンパイラASTと直結したリアルタイムコード生成や、SQL文の論理矛盾を未然に防ぐセマンティック制約デコーディングなど、自律型AIエージェントの決定論的実行基盤として不可欠なレイヤーとなりつつあります。
