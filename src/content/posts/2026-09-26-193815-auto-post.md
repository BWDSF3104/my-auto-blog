## はじめに

大規模言語モデル（LLM）の進化に伴い、単なるテキスト生成から「外部システムやデータベースと連携して自律的にタスクを遂行する」エージェント型アプリケーションへの移行が急速に進んでいます。

しかし、従来のアプローチでは、モデルごとに個別定義のFunction Callingスキーマを用意したり、独自APIラッパーを都度開発したりする必要があり、システムのスパゲッティ化やセキュリティ境界の曖昧さが大きな課題となっていました。

この課題を解決するオープン標準として登場したのが、**Model Context Protocol（MCP）**です。MCPは、LLMアプリケーション（クライアント）とデータソース・ツール（サーバー）を標準化されたプロトコルで接続するための仕様です。

本記事では、MCPのアーキテクチャの根幹を整理したうえで、TypeScriptを用いたカスタムMCPサーバーの構築手順、およびモダンWebアーキテクチャへの組み込み方を具体的に解説します。

## 詳細解説

### 1. Model Context Protocol (MCP) の全体像

MCPは、Language Server Protocol（LSP）がエディタと言語解析エンジンの関係を標準化したのと同様の思想を持っています。LLMホスト（クライアント）と、外部リソースを提供する「MCPサーバー」を疎結合に保ちます。

```
[ LLM Host / Client ] (Cursor, Claude, 自社Webアプリ)
         │
         │  JSON-RPC 2.0 (stdio / SSE)
         ▼
[ MCP Server ] (リソース / ツール / プロンプトを提供)
   ├── Resources (DB、ファイル、APIレスポンスなどの受動的データ)
   ├── Tools (データの更新、外部通知などの能動的アクション)
   └── Prompts (再利用可能なコンテキスト・プロンプトテンプレート)
```

MCPの主要な構成要素は以下の3つです。

1. **Resources**: 読み取り専用のデータコンテキスト。URI（例: `postgres://users/schema`）で識別され、LLMに必要な参照情報を安全に渡します。
2. **Tools**: LLMが実行可能な関数。入力パラメータのJSON Schemaが定義され、ユーザーの承認（Human-in-the-loop）を前提とした安全な実行制御が可能です。
3. **Prompts**: 最適化されたプロンプトのひな型。ユーザー操作を補助し、コンテキスト付きの対話を即座に開始できます。

通信層には **JSON-RPC 2.0** が採用されており、ローカル環境では `stdio`、リモート接続では `HTTP + Server-Sent Events (SSE)` を利用して双方向通信を行います。

### 2. TypeScriptによるカスタムMCPサーバーの実装

ここでは、公式SDK（`@modelcontextprotocol/sdk`）を用いて、社内チケット管理システムから課題一覧を取得し、新規チケットを発行できるMCPサーバーを構築します。

#### プロジェクトの初期設定

```bash
mkdir mcp-ticket-server
cd mcp-ticket-server
npm init -y
npm install @modelcontextprotocol/sdk zod
npm install -D typescript @types/node tsx
npx tsc --init
```

#### サーバーコードの実装 (`src/index.ts`)

```typescript
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
  ListResourcesRequestSchema,
  ReadResourceRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";
import { z } from "zod";

// ダミーデータストア
interface Ticket {
  id: string;
  title: string;
  status: "open" | "in_progress" | "closed";
}

const tickets: Ticket[] = [
  { id: "TICK-001", title: "OAuth認証のエラーハンドリング改修", status: "open" },
  { id: "TICK-002", title: "パフォーマンス計測ダッシュボードの構築", status: "in_progress" },
];

// MCPサーバーのインスタンス化
const server = new Server(
  {
    name: "ticket-management-server",
    version: "1.0.0",
  },
  {
    capabilities: {
      resources: {},
      tools: {},
    },
  }
);

// 1. Resources: チケット一覧のスキーマ・一覧を提供
server.setRequestHandler(ListResourcesRequestSchema, async () => {
  return {
    resources: [
      {
        uri: "tickets://all",
        name: "全社内チケットリスト",
        mimeType: "application/json",
        description: "現在登録されているすべてのタスクチケットのリスト",
      },
    ],
  };
});

// Resourceの実データを返す
server.setRequestHandler(ReadResourceRequestSchema, async (request) => {
  if (request.params.uri === "tickets://all") {
    return {
      contents: [
        {
          uri: request.params.uri,
          mimeType: "application/json",
          text: JSON.stringify(tickets, null, 2),
        },
      ],
    };
  }
  throw new Error(`Resource not found: ${request.params.uri}`);
});

// 2. Tools: 新規チケット作成ツールの定義を公開
server.setRequestHandler(ListToolsRequestSchema, async () => {
  return {
    tools: [
      {
        name: "create_ticket",
        description: "新しい社内課題チケットを発行します。",
        inputSchema: {
          type: "object",
          properties: {
            title: {
              type: "string",
              description: "チケットの簡潔なタイトル",
            },
          },
          required: ["title"],
        },
      },
    ],
  };
});

// Toolの実行ハンドラ
const CreateTicketSchema = z.object({
  title: z.string().min(3),
});

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  if (request.params.name === "create_ticket") {
    const parseResult = CreateTicketSchema.safeParse(request.params.arguments);
    if (!parseResult.success) {
      throw new Error(`無効な引数です: ${parseResult.error.message}`);
    }

    const newTicket: Ticket = {
      id: `TICK-${String(tickets.length + 1).padStart(3, "0")}`,
      title: parseResult.data.title,
      status: "open",
    };
    tickets.push(newTicket);

    return {
      content: [
        {
          type: "text",
          text: `チケットを作成しました: [${newTicket.id}] ${newTicket.title}`,
        },
      ],
    };
  }

  throw new Error(`Tool not found: ${request.params.name}`);
});

// サーバー起動処理 (stdioトランスポート)
async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("MCP Ticket Server running on stdio");
}

main().catch((error) => {
  console.error("Server execution error:", error);
  process.exit(1);
});
```

### 3. 実稼働における設計上の要所

WebシステムにMCPを組み込む際、特に留意すべきポイントは以下の3点です。

#### 権限分離とコンテキストの局所化
従来のFunction Callingでは、APIトークンやDB接続情報をLLMアプリ側（中央）に集約しがちでした。MCPを採用することで、「MCPサーバー単位」で接続権限を分離できます。読み取り専用のResourceと副作用を伴うToolを明示的に分けることで、プロンプトインジェクションによる予期せぬデータ破壊リスクを大幅に低減できます。

#### ステートレス性とトランスポートの選定
ローカルツール連携（CursorやCLIなど）では `stdio` トランスポートが最適ですが、Webサービス同士をクラウド上で接続する場合は `SSETransport` を用いたHTTP経由の接続を利用します。この際、リクエストごとの認証ヘッダー（JWTやOAuth2 Bearerトークン）の検証ミドルウェアをMCPサーバーの手前に配置するのが標準的なパターンです。

#### エラーハンドリングの標準化
LLMはツールのエラーメッセージからも文脈を読み取って自己修復を試みます。そのため、MCPサーバーが返すエラーレスポンスは単なるステータスコードではなく、「どのバリデーションに失敗したのか」「どのような形式でリトライすべきか」を含む有益なテキストメッセージを返送する設計が推奨されます。

## まとめ

Model Context Protocol（MCP）は、LLMと各種システムとの連携仕様を標準化し、AIエージェントのポータビリティとセキュリティを飛躍的に向上させるプロトコルです。

- **疎結合な設計**: ツールやリソースの定義をクライアント実装から切り離し、再利用可能なコンポーネントとして保守可能。
- **安全なコンテキスト提供**: Resources（受動）とTools（能動）の分離による堅牢なセキュリティ境界。
- **オープンなエコシステム**: 開発したMCPサーバーは、Webアプリケーションのみならず、CursorやClaude Desktopといった主要なAIクライアント環境から即座に利用可能。

今後は、独自のREST/GraphQL APIを生のままLLMに叩かせるのではなく、MCPサーバーを薄いファサード（Facade）として配置するアーキテクチャが、エンタープライズAI開発のデファクトスタンダードとなっていくでしょう。まずは社内の小さなデータソースからMCP化を試してみてはいかがでしょうか。
