## はじめに

LLMを活用した検索拡張生成（RAG: Retrieval-Augmented Generation）は、エンタープライズから個人向けツールまで幅広く普及しました。しかし、一般的なRAGアーキテクチャでは、ドキュメントのチャンク化、埋め込みベクトルの保存、類似度検索といったパイプラインをクラウド上のベクトルデータベース（Pinecone、Qdrant、Supabaseなど）に依存しています。

この構成には、**「社外秘データや個人情報をクラウドに送信するリスク」**や**「インフラコストの増大」**、**「オフライン時の動作不可」**という課題がつきまといます。

そこで注目されているのが、**「Local-First（ローカルファースト）」なAIアーキテクチャ**です。本記事では、PostgreSQLをWebAssembly（WASM）としてブラウザ内で軽量動作させる「**PGlite**」と、そのベクトル拡張機能「**pgvector**」を活用し、サーバーを介さずブラウザ内で完結する高速・セキュアなベクトル検索エンジンの実装方法を解説します。

---

## PGliteとは？ なぜブラウザ内でPostgreSQLなのか

[PGlite](https://pglite.dev/)は、ElectricSQLチームが開発したPostgreSQLの公式C言語コードベースをWebAssembly向けにコンパイルした埋め込み型データベースエンジンです。

従来のブラウザ内SQLといえばSQLite（SQL.jsやsqlite3-wasm）がデファクトスタンダードでしたが、PGliteには以下の強力な利点があります。

1. **pgvector拡張の標準サポート**: PostgreSQLで広く使われているベクトル類似度検索拡張機能（`pgvector`）がそのままブラウザ上で動作する。
2. **IndexedDB連携による永続化**: 単なるインメモリDBではなく、ブラウザのIndexedDBストレージへ自動的に永続化可能。
3. **軽量フットプリント**: Gzip圧縮時で3MB程度と、Webアプリケーションのアセットとして実用的なサイズ。
4. **標準SQLとの互換性**: フルテキスト検索（`tsvector`）や高度なJOIN、トランザクションが利用可能。

これにより、ブラウザの内部に「ミニSupabase」を抱えるような開発体験が手に入ります。

## 実践：ブラウザ内ベクトル検索の実装

ここからは、TypeScriptとPGliteを用いて、ドキュメントの登録とベクトル検索を行うミニマムな実装手順を紹介します。

### 1. 依存パッケージのインストール

PGliteとpgvector拡張パッケージをインストールします。

```bash
npm install @electric-sql/pglite
```

### 2. PGliteの初期化とpgvectorの有効化

PGliteインスタンスを立ち上げ、IndexedDBに永続化する設定を行います。さらに、拡張機能として`vector`をロードします。

```typescript
import { PGlite } from "@electric-sql/pglite";
import { vector } from "@electric-sql/pglite/vector";

// IndexedDB上の 'idb://local-rag-db' にデータを永続化
const db = new PGlite("idb://local-rag-db", {
  extensions: {
    vector,
  },
});

async function initDatabase() {
  // pgvector拡張を有効化
  await db.exec("CREATE EXTENSION IF NOT EXISTS vector;");

  // 384次元の埋め込みベクトルを持つテーブルを作成
  // （例: all-MiniLM-L6-v2 などの軽量埋め込みモデルを想定）
  await db.exec(`
    CREATE TABLE IF NOT EXISTS documents (
      id SERIAL PRIMARY KEY,
      content TEXT NOT NULL,
      metadata JSONB,
      embedding vector(384)
    );
  `);

  // コサイン距離のHNSWインデックスを作成して検索を高速化
  await db.exec(`
    CREATE INDEX IF NOT EXISTS documents_embedding_idx 
    ON documents USING hnsw (embedding vector_cosine_ops);
  `);

  console.log("Database initialized successfully!");
}
```

### 3. ベクトルデータの挿入

ドキュメントのテキストと、その埋め込みベクトル（配列）をデータベースに保存します。

```typescript
interface DocumentItem {
  content: string;
  metadata: Record<string, any>;
  embedding: number[];
}

async function insertDocument(doc: DocumentItem) {
  // pgvectorの形式 '[0.01, 0.02, ...]' に変換して保存
  const vectorString = `[${doc.embedding.join(",")}]`;

  await db.query(
    `INSERT INTO documents (content, metadata, embedding) 
     VALUES ($1, $2, $3::vector)`,
    [doc.content, JSON.stringify(doc.metadata), vectorString]
  );
}
```

### 4. コサイン類似度による類似チャンクの検索

ユーザーのクエリから生成されたベクトルをもとに、コサイン距離演算子（`<=>`）を使用して類似度の高いドキュメントを抽出します。

```typescript
async function searchSimilarDocuments(
  queryEmbedding: number[],
  limit: number = 3
) {
  const vectorString = `[${queryEmbedding.join(",")}]`;

  // コサイン距離が近い順（1に近いほど類似）にソート
  const result = await db.query<{
    id: number;
    content: string;
    similarity: number;
  }>(
    `SELECT 
       id, 
       content, 
       1 - (embedding <=> $1::vector) AS similarity
     FROM documents
     ORDER BY embedding <=> $1::vector ASC
     LIMIT $2;`,
    [vectorString, limit]
  );

  return result.rows;
}
```

## Local-First RAGのアーキテクチャ設計

ブラウザ内ベクトル検索を実運用に組み込む場合、以下のようなハイブリッド構成が推奨されます。

```text
[ ユーザーの入力 ] 
       │
       ▼
[ Web Worker (埋め込み生成) ] 
       │ （Embedding Vector）
       ▼
[ PGlite + pgvector (IndexedDB) ] ── (類似テキスト抽出) ─┐
                                                         │ (プライベートなContext)
                                                         ▼
[ 外部LLM API または ローカルLLM ] ◀────────────────────┘
       │
       ▼
[ 生成された回答の表示 ]
```

### 考慮すべきポイント

1. **埋め込みモデルの実行環境**:
   埋め込み生成処理はメインスレッドをブロックしないよう、Web Worker内で実行するか、セキュアなバックエンドAPIからベクトル値のみを受け取る設計にします。
2. **インデックスの選定（IVFFlat vs HNSW）**:
   メモリが限られるブラウザ環境では、ドキュメント数が数千件程度であればFlat検索（ブルートフォース）でもミリ秒単位で完了します。1万件を超える場合はHNSWインデックスを構築することで高速な検索レイテンシを維持できます。
3. **ストレージ容量の管理**:
   IndexedDBはブラウザによって数GB〜数十GBまで使用可能ですが、ストレージ圧迫通知やキャッシュクリアに備え、ドキュメントの元データをエクスポート／インポートする機能を用意しておくと堅牢です。

## まとめ

PGliteとpgvectorの登場により、これまでサーバー側のリソースを大量に消費していた「ベクトル検索」を、完全にクライアントサイドへオフロードできるようになりました。

このアプローチは以下の圧倒的なメリットをもたらします。

- **プライバシー保護**: 社内ドキュメントや個人メモがブラウザの外に一切流出しない。
- **インフラコストゼロ**: ベクトルDBのホスティング費用・転送費用が不要。
- **オフライン稼働**: ネットワークが途切れてもドキュメント検索機能が停止しない。

Local-First思想とWebAssembly技術の進化は、AIアプリケーションのアーキテクチャを大きく変えつつあります。機密性の高いドキュメント管理ツールやナレッジベースを開発する際は、ぜひ「ブラウザ内Postgres」という選択肢を検討してみてください。
